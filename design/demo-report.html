2两种控制方式架构对比

A. 传统 · onClick / 事件内重绘

ACTION_DOWN → 等待抬起
ACTION_UP + TouchSlop 确认 → onClick（固有 ~150ms 延迟）
在 onClick / onTouchEvent 内同步：关键帧插值 + drawBitmap + invalidate()
主线程被占 → 下一帧 Vsync 来不及绘制 → 首帧掉帧
手势在事件内直接重绘，事件序列易被父容器截断

B. 优化 · Choreographer / RAF 帧驱动

ACTION_DOWN 即时触发播放（不等抬起，指哪打哪）
Choreographer.doFrame / requestAnimationFrame 对齐 Vsync
doFrame 内只做插值计算 → 存入 pose；onDraw 只读 pose 纯绘制
计算与绘制解耦，下一帧 Vsync 准时提交
指针手势经 Matrix.invert() 映射局部坐标，requestDisallowInterceptTouchEvent 按时机释放

关键代码（优化模式核心）

// 帧驱动：计算与绘制彻底解耦，逐帧对齐 Vsync
override fun doFrame(frameTimeNs: Long) {
  if (!playing) return
  currentFrame += dt * fps
  onPoseReady?.invoke()              // → view.invalidate()，仅通知重绘
  Choreographer.getInstance().postFrameCallback(this)
}
// 渲染层 onDraw 只读 pose，不计算
fun sampleAll(): Map<String,Float> = tracks.mapValues { it.value.sample(currentFrame) }
// 手势：屏幕点经逆矩阵映射回骨骼局部坐标
val local = canvasMatrix.invert()!!.map(rawX, rawY)   // Matrix.invert() 失败需保护

关键代码（传统模式病灶）

// 在事件回调里既算又画 —— 主线程阻塞、首帧掉帧
btn.setOnClickListener {
  busyWork()                       // 关键帧插值 + drawBitmap（~9ms 阻塞）
  skeletonView.invalidate()       // 在 onClick 内直接重绘
}
// onTouchEvent 直接 return super，且分支 return false → 事件序列被截断
维度传统 onClick优化 RAF
输入→首帧延迟~150ms（等抬起+TouchSlop）≈1 帧（~16ms）
帧驱动时钟 / 事件内手动重绘Choreographer 对齐 Vsync
计算 vs 绘制混在一起，阻塞 UI解耦（doFrame 算 / onDraw 画）
手势映射用 getX/Y，忽略 View 偏移/旋转Matrix.invert() 逆映射局部坐标
系统手势冲突return false 提前交还父容器onScroll 确认后再 disallow，UP/CANCEL 释放
典型结果帧率↓、延迟高、丢帧明显满帧、跟手、几乎无丢帧

4结论与导师指引映射

结论：把骨骼动画的帧驱动从 onClick 迁到 Choreographer/requestAnimationFrame， 并将「关键帧插值计算」与「Canvas 重绘」解耦，是消除点击迟滞、首帧掉帧、手势断续的决定性架构调整——与导师在 事件分发、Vsync、主线程阻塞三点的判断完全一致。

手势侧：用 Matrix.invert() 把屏幕触摸点逆映射回骨骼局部坐标系（而非手动减偏移）， 并遵循「确定性」原则——ACTION_DOWN 不抢事件、onScroll 确认滑动后再 requestDisallowInterceptTouchEvent(true)、ACTION_UP/CANCEL 释放——同时解决了轨迹跳变与系统手势冲突。
